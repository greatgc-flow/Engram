## §0. Activation Gate — read this first

Do not implement §3 onward unless **all five** conditions hold, per cx.deepthink's round-7/9 formulation:

1. A named integration with an accountable owner.
2. Committed delivery/deployment intent — not exploratory interest, not a whiteboard "someone might want this."
3. A concrete end-to-end use case the existing CLI/library cannot appropriately satisfy.
4. Executable conformance fixtures covering that consumer's telemetry, quota, effects, and failure semantics.
5. Agreement that the consumer will maintain or fund the resulting compatibility surface.

Two independence tests (fable, round 7): would this consumer want the integration even if Engram had never designed this protocol (a conjured consumer fails)? And separately — an observed operational bug whose root cause demonstrably *is* the monolithic structure (i.e., a fix was attempted in place and cost more than a seam would have) is a **second, independent trigger class**: under-fitting announces itself loudly; that announcement, not projection, is the real build signal.

A monolith-caused operational failure may **reopen review**. It does not auto-activate implementation. **Fresh R:10 unanimous consensus is required either way**, citing which trigger fired and against which named consumer or measured failure.

**Process amendment adopted this round** (fable, round 7, unanimous): deferral must be symmetric with addition. Adding scope back into an active plan requires the same explicit consensus as removing it did. The default between any two review rounds is the smallest surviving plan. A "deferred" item carries zero implementation obligations until the gate fires — it does not accrete into a "deferred but mandatory" item (this happened live during the debate itself with client-attribution guardrails in round 6-7, and was explicitly reversed in round 7's subtraction pass).

## §2. The bug this debate found (evidence, not architecture)

Answering a concurrency-model question about the *shelved* design (round 3's Q9), fable and cx independently source-inspected `hub.py` and cx additionally reproduced it empirically with a disposable probe:

- **Lease clobber**: `_lease_open` writes `data[peer_id] = entry` (`hub.py:8998`) — keyed by `peer_id` alone. Two concurrent asks to the same peer/profile in the same room: the second open overwrites the first's lease unconditionally.
- **Silent close no-op**: `_lease_close` guards on `data[peer_id].get("pid") == pid` (`hub.py:9021`); after a clobber, the first ask's close silently no-ops.
- **Unguarded renew**: `_lease_renew` (`hub.py:9010`) has *no* pid guard at all — the first ask's heartbeat loop keeps renewing the second ask's (clobbered) entry, corrupting its heartbeat/expiry evidence.
- **Session-state lost update**: `_set_active_session` reads before `_save_session_state` takes its `ss_{peer_id}` lock (`hub.py:3501-3524`) — two concurrent writers can both read the same base state; the loser's `active` entry is silently dropped.
- **Empirical confirmation** (cx, round 4): a disposable, non-production probe opened two leases for `cx` with distinct ask IDs/PIDs — only one record remained after both opens; closing the first PID left the second's record open. `[empirical_probe]`.
- **Coverage gap confirmed**: `test_locking_stress.py` covers `test_parallel_init_session` and `test_concurrent_consensus_votes`, nothing exercises two concurrent asks to the same peer or concurrent session reuse.
- **Masking condition**: today's "one coordinator per room" usage pattern happens to avoid triggering this. DIR-006 consensus rounds already fan out concurrent asks to *different* peers safely; the moment two profiles sharing a root peer's lease handling run concurrently, the mask slips. Production incidence beyond the disposable probe remains `TEST NEEDED` — not yet observed in a real user session.

Fix design: §1 item 2.

## §4. Concurrency, crash recovery, and budget-reservation lifecycle (shelved)

Three separate state machines, not one:

- **Room-coordinator lease**, keyed by `room_id`, carrying a monotonically increasing fencing epoch. Every governed room mutation presents the current epoch, so a revived stale coordinator cannot write after a takeover.
- **Request lease**, keyed by `request_id` (not `peer_id`, not the shelved architecture's equivalent of today's weak `ask_id`), carrying peer/profile, coordinator epoch, PID + process-birth identity, dispatch state, heartbeat, expiry.
- **Machine-scope budget reservation**, keyed by `reservation_id`, linked to `request_id` and `quota_pool_id`. Lifecycle: `reserved → dispatch_intent → launched → consumed / released / consumed_unknown`. Locks are held only during atomic state transitions, never during the model call itself.

Recovery contract: persist `dispatch_intent` before spawn, PID/process identity + `running` after spawn. **Never kill from PID alone** — PID reuse can target an unrelated process. An expired request with a verified-live child is fenced and terminated; a dead child is marked `interrupted`. Requests that reached `dispatch_intent` are **not** automatically replayed (invocation/quota-use/side-effects may already have occurred) — only a request definitely still pre-dispatch may be safely requeued. A crashed session is marked uncertain, not reused, unless a provider independently verifies it. Recovery emits a durable terminal `interrupted` event so clients don't wait forever. Budget reservations: only definitely-pre-launch reservations may be released after a short TTL; anything that reached `dispatch_intent` is conservatively charged `consumed_unknown` — this separates the crash-recovery TTL from the H1/H2 accounting window, deliberately.

Migration-window hazard (fable, round 6, applies **only once peer migration actually starts**, i.e. after §0 fires): peer-by-peer porting means the old `hub.py` path and the new Engram path both touch spend for a period — two independent enforcers of one cap is not a cap (double-counting or missed-counting). Mitigation: **the budget ledger migrates first, alone, before any peer** — old `hub.py` becomes a write-through client of the new ledger, establishing exactly one accounting authority on day one of migration, before any peer port begins. (This is why §1 item 3 ships only a test today — there is no second writer yet to arbitrate between.)

## §5. Protocol versioning contract (shelved)

Independent wire SemVer starting at `1.0.0` (never conflated with the package version). Negotiate before any side effect: first frame each direction is a `hello`/`initialize` carrying supported version ranges and capabilities; the server selects a version; out-of-range fails with a typed `VERSION_MISMATCH` naming the supported range, never a parse failure. Patch releases touch only docs/diagnostics/validators. Minor releases are strictly additive (new optional fields, new `skippable`-flagged event types, new opt-in capabilities) — all readers are contract-tested to skip unknown fields/events without error; that's what makes additive-only actually safe. Major releases carry breaking changes, with a deprecation runway (a field/event spends ≥1 minor release marked deprecated *and* emits a runtime `deprecation` notice before removal; removal requires the later of 180 days or two minor releases after deprecation). Support window: current major + N−1, dropped only with a stated notice period. CI enforcement: schema-diff against the last released version (fails on non-additive change without a major bump), golden-transcript replay against every supported major, old-client/new-server and new-client/old-server bidirectional conformance tests, unknown-field/skippable-event tests. Every streamed record carries `request_id`, monotonic `seq`, `room_id`, event type, negotiated wire version.

Old-CLI-talks-to-new-service (and the reverse, briefly, during upgrade) is a **normal supported operating state**, not an edge case — it follows directly from the service being long-running and the CLI being separately upgradable. Deployment: manual `pipx upgrade engram` / `pip install --upgrade`, no `engram self-update`, a passive non-blocking staleness notice only (never auto-installing) — reintroducing active update-checking for Engram's own binary would be inconsistent with this same debate voting `check_tool_updates.py`-style checking out of core (§3, D3 rationale). A CI matrix job runs the previous released CLI against the current service's protocol surface, so "supported skew" is a tested claim, not a declared one.

## §6. Governance model for the new package (shelved)

Not uniform PRO-12/R:10 on every commit — that either makes trivial adapter boilerplate cost three-peer unanimity (degrading the gate's signal exactly where it matters) or forces ad-hoc exceptions (which corrode it). **Effect-based, not directory-based** classification (cx's refinement, round 4, adopted by all three): a change in `adapters/` that alters permissions, process-kill behavior, or evidence provenance is critical regardless of its directory. Mechanically tractable via a **hybrid** (fable, round 4): a directory tier as the cheap deterministic floor, plus a small auditable registry of *effect-carrying symbols/files* (permission-flag construction, process-kill helpers, evidence-writing paths, wire-schema files) — a diff touching any registered symbol auto-promotes to the critical tier. A pure semantic-diff CI classifier was explicitly rejected as untractable and untrustworthy for a security-relevant control ("a control that doesn't enforce is the exact failure DIR-002's history warns about," fable). The classifier can only fail *safe*: a reviewer may promote anything; demoting an auto-promoted change requires the full critical-tier process.

Tiers: **A** (full R:10 per commit) — domain logic, policy-merge/budget/canary enforcement, the `engram.api` facade, protocol schemas, the tier-map file itself (whose own changes are Tier A + user ratification, closing the obvious escape hatch). **B** (one-peer review + green contract tests) — adapters, transports, peer descriptors. **C** (green tests, post-hoc reviewable) — CLI presentation, docs, formatting. Any mixed commit takes its strictest touched tier. Note (fable): D4's registration invariant *shrinks Tier A over time* — once peer knowledge can't leak outside the providers package, most day-to-day change lands in B/C, which is the actual payoff justifying the split. DIR-006 still requires unanimous direction/architecture agreement; it does not require re-voting every implementation commit inside an already-agreed plan.

## §7. Testing pyramid (shelved) and disposition of today's 1261 tests

Five layers, plus governance-tier CI checks as a cross-cutting gate (not a layer): **(0) architecture tests** — the D4 no-concrete-peer-identifier invariant, import-linter style, given a durable home rather than living as an unowned CI script. **(1) domain/unit, the bulk** — pure logic against `engram.core`, no I/O: budget state machines, lease/fencing, routing, governance tiers. **(2) adapter/provider contract tests** — per-`PeerAdapter` and per-`UsageProvider` (including the valid no-provider case) against fakes, plus a small opt-in tagged live-probe suite for DIR-004 empirical evidence, scheduled, never CI-blocking. **(3) wire/facade contract tests** — `engram.api` + JSONL both directions, malformed/truncated input, error mapping, cancellation, duplicate requests, version negotiation, current↔previous-major fixtures (golden, append-only per released version, never edited retroactively). **(4) integration/fault tests** — real transport runner, fake peer executables, concurrent clients, crashes injected at every §4 lifecycle transition. **Smoke** — single digits: one real `collaborate` round-trip through the real transport against a fake peer binary.

Characterization tests are an explicit **temporary migration overlay**, stated as such in this document precisely so they don't accrete into an unplanned permanent sixth layer (fable's warning, round 5).

Disposition of the current 1261 tests: **classified and split, not blindly ported and not wholesale rewritten.** Majority move to domain/unit tests where the PathLayout seam and behavior-preserving extraction make that mechanical; peer-specific cases move to adapter/provider contract suites; CLI-observable behavior becomes facade/wire contracts; hub-internal white-box tests stay as characterization tests until their extraction lands, then retire (the exact pid-keyed lease structure the confirmed bug lives in is a named example of a test that should be *rewritten*, not ported, since it asserts internals the fix deliberately kills). Governing principle: **behavioral coverage never decreases; test count is allowed to.**

## §8. Client trust, attribution, and blast radius (shelved)

Same-OS-user process trust is treated as the **sole v1 security boundary if this activates** — sufficient for security (a same-user process can already read `~/.engram/` config and spend budget directly regardless of any client-side gate; tokens, binary-path allowlists, and first-connection consent prompts were explicitly rejected as theater against a process that already shares OS-level access), but explicitly insufficient for accountability. `engram.initialize` requires a mandatory, self-declared, cooperative-labeling-only `client_name`/`client_version`/`client_instance_id`/`connection_id` plus a `client_kind: interactive | automated` field — not authentication, purely attribution, denormalized into every budget-ledger row so "which client burned the budget" is a one-line query. Full fair-share scheduling is explicitly out of scope even if activated (cap=4/12h cannot be meaningfully partitioned across N clients); what's in scope: per-client in-flight/queue admission limits as a stability backstop (not a fairness scheduler), mandatory idempotency keys so retries never consume fresh reservations, and reinterpreting the already-ratified `reserve_floor=0.25` (this session's H1/H2 ratification) as "the reserved fraction is spendable only by `client_kind=interactive`" — guaranteeing the human terminal one canary slot even if an automated client drains the rest, at the cost of two lines of policy, not a scheduler.

Fault-containment risk flagged in round 6 (cx) and never fully resolved — **carry this into any future activation as an open item, not a solved one**: centralizing admission/accounting risks turning one peer's slow/hung usage provider into a machine-wide outage, where today's peer-specific system keeps such a failure localized. Before activating this architecture, it needs empirical fault tests for indefinitely-blocked, extremely-slow, and resource-exhausting providers — the centralization premise is unproven without them.
