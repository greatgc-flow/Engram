## Zombie phenomenon: found, measured, and fixed (partially)

**Diagnosis** (4/4 responding peers converged, using real telemetry, not the prompt's characterization alone): a stalled `ag` run can go completely silent mid-stream *after* producing genuine progress, and never resume. This is neither "ag is slow" (a successful retry of the identical failed query took *longer* in total — 1399s vs 983s — but never had a silence gap near the zombie threshold) nor "ag batches and dumps everything at the end" (the successful run shows continuous output arrival all the way to completion, not one large terminal burst). The existing 600s/900s zombie window was being reapplied in full from the *last* observed chunk, wasting hundreds of seconds of dead time before killing an already-dead process.

**Fixed** (`e1e35e2`): `_effective_zombie_timeout_sec()` in `hub.py` tightens the silence-kill window to 300s once genuine PTY output has been observed past a 100-byte noise floor (all 88 historical records started with ~23 bytes of PTY-init noise; a naive "after any byte" rule would recreate a previously-retired false-positive regression that killed 3 real, still-working `cx` calls in 2026-06). Cold-start behavior is unchanged. Replayed against the exact measured 2026-07-17T15:56 zombie case: kill now fires at ~683s instead of 983s (300s saved), matching all 4 peers' independent calculation. Unit-tested (`test_zombie_post_progress.py`), including a direct replay of the real measured case.

**Deliberately not implemented tonight**: automatic retry-on-zombie. All 4 peers proposed some form of single bounded retry as the highest-leverage remaining fix (the exact same query succeeded on manual retry), but 2 of 4 (both cx voices) raised a specific, well-reasoned safety concern: a zombie kill happens *after* the process was dispatched, so real side effects (e.g. a worker peer's file edits) may already have occurred server-side before the silence was detected, and blind retry risks duplicating them — `hub.py` already deliberately suppresses post-spawn auto-retry elsewhere for exactly this reason. Implementing this safely requires threading an explicit opt-in flag through `action_ask()` → `_action_ask_inner()` and choosing the right insertion point relative to the existing lease/cleanup `finally` block — real design work, not a same-session addition after an already very long session. **Concrete next-step design** (converged across all 4 peers): a single bounded retry, gated behind an explicit flag (never default-on), linked attempt IDs, telemetry for original/retry outcome and time saved, restricted to callers that can assert the ask is replay-safe.

## Critical, unrelated finding: 41GB process leak (found while investigating zombie connectivity)

While cx.deepthink was investigating why its own nested dispatch attempts were failing, it found — as a side discovery, not something asked for — that the host had accumulated **558+ orphaned `node.exe` and 558+ orphaned `codex.exe` processes** at roughly one-per-minute. Independently verified by the terminal: **1118 processes, 41GB of working-set memory**, confirmed live via `Get-Process`.

**Root cause**: `snapshot.py`'s Codex rate-limit probe (`_codex_rate_limits()`, called on the `diag`/`diag --live` 60-second expensive-source TTL) launches `codex.cmd` — a 3-level chain (`cmd.exe` → `node.exe` → `codex.exe`) — via `subprocess.Popen`, but its cleanup only called `proc.kill()` on the `Popen` handle, which kills just the immediate `cmd.exe` wrapper. `node.exe` and `codex.exe` were orphaned every single probe cycle, forever, with zero reaping.

**Fixed** (`f26dfed`): replaced `proc.kill()` with a `taskkill /F /T` full-tree kill. Unit test updated to assert the tree-kill actually fires. The pre-existing 1118 leaked processes were cleaned up as a one-time manual pass (user-approved, precisely PID-scoped rather than by image name to avoid any risk to unrelated legitimate `node.exe`/`codex.exe` processes — verified via command-line inspection that literally 100% of both process names on the host were part of this leak at the time).

This is very plausibly a real contributor to *other* instability observed tonight (an unrelated OOM-guard trigger during a peer's test run, and repeated transient RED health-flapping on `ag` and `cc` that self-cleared within seconds) — 41GB of leaked memory and 1000+ zombie processes put real, continuous pressure on the whole host, not just on `diag`.
